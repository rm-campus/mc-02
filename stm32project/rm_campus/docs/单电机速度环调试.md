# M3508 / C620 单电机速度环调试

这份代码用于架空底盘逐台调试，尚未实现四麦轮运动学。控制链为：右摇杆上下 → 输出轴目标速度 → 目标速度斜坡 → MC02 速度 PI → CAN 电流指令 → C620 内部电流控制。

## 1. 先认识文件和默认行为

| 文件 | 用途 |
| --- | --- |
| `App/Inc/motor_debug_config.h` | 选择 C620 编号、开关、PI 参数及限幅；日常调参改这里 |
| `App/Src/motor_debug.c` | 使能状态机、目标斜坡、速度 PI、抗积分饱和 |
| `App/Src/campus_app.c` | 1 ms 底盘任务读取反馈、统一发送四路电流；监测任务输出 USB 文本 |
| `tests/run_motor_debug_tests.py` | 电脑上的控制器回归测试，不连接硬件 |
| `scripts/build_firmware.ps1` | 使用本机 CubeIDE 工具链构建，不下载固件 |

**当前交付的 `MOTOR_DEBUG_ENABLE=0`，Kp=Ki=0。四路电流始终为零。** USB 观测默认开启，10 Hz。只连接 USB、推摇杆、发送串口字符都不会解除编译开关。

反馈速度已由底层换算为 M3508 减速箱输出轴 rad/s，不要再除一次减速比。`rpm = rad/s × 60/(2π)`。若轮子通过额外传动连接输出轴，需要另外考虑传动比。

## 2. 第一次：只验证通信和编号

1. 固定底盘，使四个轮子全部离地；测试场地应允许轮子自由转动。安排一人操作遥控、一人能立即断电。首次调试不落地，不用手阻挡通电转动的轮子。
2. 断电检查供电极性、电压和接头；MC02 使用 **FDCAN3** 接 C620 的 CAN，CAN_H/CAN_L 对应，确认终端电阻及电调 ID 唯一。不要带电改接电源、CAN 或电机线。编号识别/设置按 C620 官方说明；不要仅凭线的排列猜编号。
3. 保持默认配置，编译并用 ST-LINK 下载。**本次开发没有替你下载到板子。** 确保下载的是本次编译的 ELF，而非旧工程产物。
4. 用数据 USB 线连接 MC02 的 USB 接口，电脑打开它枚举出的 CDC 串口，文本接收；终端可选 115200、8N1。这里是 USB CDC，所选串口波特率不决定 SBUS 速率。ST-LINK 的下载连接与此观测串口是两条用途不同的链路。
5. 检查 `rc=1`。按团队实测映射，上下移动右摇杆（CH3）时 `joy` 应在约 -660～660 变化，移到中位时接近 0。单独上下移动左摇杆（CH2）时 `joy` 应保持不变。正常手持遥控器，拨动面板最左拨杆（CH7）观察 `sa`，确认关闭档为 -1、启用档为 1。
6. `on` 是在线掩码，bit0～bit3 对应 C620 ID1～4；四台都在线为十进制 **15**。默认不输出电流时，可轻轻转动一个轮子，观察 `w=a/b/c/d` 哪一项变化，据此记录 ID 与轮子的对应关系。如果只连一台电调，它对应的那一位在线即可进行单台测试，不要求其余三台在线。
7. 确认摇杆回中落在 ±40 内。若 `rc=0`、编号重复或电机反馈不稳定，先解决通信，不打开调试开关。

| C620 ID | 实际轮子 | 正指令转动方向 | Kp | Ki | 架空效果 | 落地后复核 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 待填 | 待填 | | | | |
| 2 | 待填 | 待填 | | | | |
| 3 | 待填 | 待填 | | | | |

## 3. 第二次：启用一台电机

关闭电机供电，打开 `App/Inc/motor_debug_config.h`，例如先测 ID1：

```c
#define MOTOR_DEBUG_ENABLE 1
#define MOTOR_DEBUG_MOTOR_ID 1U
#define MOTOR_DEBUG_KP 0.05f
#define MOTOR_DEBUG_KI 0.0f
```

0.05 只是保守的空载起试值，并非实物已整定参数，可能不足以让轮子转动。保留默认最大目标速度 3 rad/s、斜坡 2 rad/s²、电流限幅 1 A，不直接照搬其他工程不同速度单位下的 PID 数字。

重新编译、下载。**仅 ID1 可获得非零电流，ID2～4 仍发送零电流。** 用以下顺序操作：

1. 遥控有效、目标电机反馈新鲜、CAN 正常；把已确认的启用开关拨到 `sa=-1`。
2. 右摇杆上下回中，待轮子基本静止，再拨至 `sa=1` 并保持回中至少 300 ms。
3. `st=3` 表示已经启用；轻推右摇杆上下，先小幅正向，再回中，再小幅反向。电机方向先记录，不急着用方向掩码改轮子前进定义。
4. 摇杆回中：目标按斜坡降到零，速度环继续工作，可产生制动电流。开关回到关闭档或中档：**立即将指令电流置零**，这时轮子可能滑行，不能把撤流当作机械刹停。
5. 每次启用最多运行 10 s；超时后回关闭档、回中，再启用。任何故障后也必须重新执行此顺序，通信恢复不会自动恢复转动。

目标斜坡约束的是软件目标变化率，不能保证实际车体加速度。它不是加速度反馈环。调试模式尚未配置硬件急停/看门狗；程序卡死、总线损坏时，零电流帧不保证能够送达，因此台架必须保留独立断电手段。USB 断开仅失去观测，**不会**作为停机条件。

## 4. 看懂数据和故障

示意（不是实测）：

```text
DBG t=1234 st=3 why=0 id=1 rc=1 sa=1 joy=350 on=15 dt=1 tgt=1500 ref=600 vel=500 out=50 cur=40 temp=28 w=500/0/0/0
```

| 字段 | 含义 |
| --- | --- |
| `t`, `dt` | HAL 毫秒时间戳、本次控制间隔 ms；正常 `dt` 约 1 |
| `st` | 0 编译关闭；1 等待关闭确认/故障；2 已见关闭档，等待启用回中；3 运行 |
| `why` | 见下表；故障原因在等待关闭时保留，健康地拨到关闭档后清除 |
| `id`, `rc`, `sa`, `joy` | 目标 C620 ID、遥控是否在线、开关枚举值、右摇杆上下原值 |
| `on` | 四电机在线位掩码，不代表运动使能；1/2/4/8 分别为 ID1/2/3/4 |
| `tgt`, `ref`, `vel` | 摇杆目标、斜坡后参考、目标电机实测速度，均为 **rad/s × 1000** |
| `out`, `cur` | PI 指令电流和目标电机实测电流，均为 **A × 1000，即 mA** |
| `temp` | 目标电机 C620 反馈温度，°C |
| `w` | ID1/2/3/4 的实测速度，均为 rad/s × 1000 |

例：`ref=600` 是 0.600 rad/s；`out=50` 是 0.050 A，均不是 CAN 协议原始值。调试器 `Campus_CopyMotorDebug` 快照中的浮点数直接使用 rad/s 和 A。USB 队列忙会丢弃本条观测；10 Hz 文本适合基础观测，不能据此证明 1 kHz 时序或高频振荡完全正常。

| `why` | 原因及检查方向 |
| --- | --- |
| 0 | 无故障；若 `st=0`，需要修改编译开关后重新构建下载 |
| 1 | 配置非法：ID、参数单位和限幅是否在代码允许范围内 |
| 2 | 遥控无效/超过 100 ms 没有有效帧，或通道值越界 |
| 3 | 选中的电机从未反馈或反馈超过 50 ms，检查 ID、供电和 CAN |
| 4 | CAN 初始化/状态查询失败、Bus-Off 或发送入队失败 |
| 5 | 控制间隔为 0 或超过 5 ms，检查任务阻塞/调度；不要简单放宽阈值掩盖问题 |
| 6 | 反馈温度达到默认 70°C，断电检查并等待冷却 |
| 7 | 非有限反馈，或实测速度达到默认 8 rad/s，检查反馈、控制方向和增益 |
| 8 | 本次运行达到 10 s 限时；回关闭档、回中后重新启用 |

只有目标电机反馈参与单台启用判断。LED 依然按“CAN、遥控、四电机是否在线”显示，绿色不能替代 `st` 的运动使能状态。

## 5. 调参顺序

1. **先 P 后 I，D 保持没有。** 在固定的小幅摇杆目标下观察 `ref` 与 `vel`。从 Kp=0.05、Ki=0 开始，一次小幅增加 Kp，记录每次参数和响应。如果发生抖动、啸叫、速度快速增大或明显发热，立即关闭使能并断电检查；不要继续增加增益。
2. 如果 `out` 很小而轮子不动，可逐步增加 Kp；如果 `out` 已长时间贴近 1000 mA，而速度仍跟不上，先查机械卡滞、供电、型号和单位。不要一味加 Kp/限流，也不要手堵转测试。
3. P 稳定后若有持续稳态误差，从小 Ki 开始补偿，例如 0.02，再逐步观察。这里 `I += Ki × error × dt`，dt 已用秒计算，和“每周期直接累加”的旧 PID 代码单位不同。积分项默认限 0.3 A，饱和时停止同向累积；停用/故障会清积分。
4. 每次改参数都在关闭使能、断开电机动力后重新编译下载，避免在运行中用断点修改参数或单步执行。暂停 MCU 会停止周期保护和指令更新，不能当作安全停车。
5. 当前轮子通过后，把 `MOTOR_DEBUG_MOTOR_ID` 改为 2、3、4，分别验证。相同硬件可以用同一组初值，但要逐台确认；本功能一次只保存一个 PI 状态，不同时控制四台。
6. 四台架空都正常后，再开发四路独立 PI 状态、麦轮运动学、整车限速和落地低速测试。空载参数不能直接认为落地也已调好。届时再测轮径、轮距和轴距。

## 6. 编译和验证

在工程目录运行（安装位置不同可传 `-CubeIdeHome`）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build_firmware.ps1
```

脚本只构建，不烧录、不发送硬件指令。正常输出为 `build/BenchDebug/rm_campus.elf`。需要 Python 3，当前电脑已安装。CubeIDE 已导入的链接源码目录就是本工程；重新生成 CubeMX 代码不是本次修改的必要步骤。下载前在启动配置中核对 ELF 路径。

本次本机 CMake 在工具链识别时异常退出（`0xC0000409`），更换便携版和路径后仍可复现，根因尚未确定。因此提供上述**备用 ARM GCC 直接构建脚本**：读取当前工程 CMake 中的源码/头文件清单，按现有 STM32H723 Debug 配置编译链接，跳过 CMake 配置程序。本机完整的 78 个源码已通过 ARM 编译和链接。该脚本只针对当前模板；将来更改 MCU、编译选项或使用条件化 CMake 源码清单时，需要同步维护备用构建配置。正常 CMake 工程也已添加 `motor_debug.c`，不需要改成别的工程类型。

如果 CubeIDE 的 Build 同样在配置阶段退出，先用备用脚本生成 ELF，再在 CubeIDE 的调试启动配置中将 C/C++ Application 指向它，并关闭该启动配置自动执行的失败构建步骤。每次改代码，先运行脚本成功，再启动下载。不要把旧 ELF 当作刚修改后的程序。

电脑上运行控制器测试：

```powershell
python tests/run_motor_debug_tests.py
# GCC 不在 PATH 时：
python tests/run_motor_debug_tests.py --cc D:/tools/MinGW/bin/gcc.exe
```

主机测试仅验证软件逻辑和简化模型，不能替代实板反馈、接线、控制周期、急停和机械验证。
